# 자료 보존 업데이트 적용 절차

## 적용 범위

로그인, 세션, 인증·권한 로직은 이번 수정 대상에서 제외했다. 서버 쓰기 점검 표시와 구버전 화면 차단은 자료 보존을 위한 장치다. 로그인도 동의 일시를 기록하므로 점검 중에는 잠시 중단된다.

| 문제 | 변경 내용 |
| --- | --- |
| 평가 회차 구분 | 회차 생성·선택·필터 추가. 같은 대상·종류도 다른 회차에서 새 프로젝트 생성 가능 |
| 과거 평가 변경 | 프로젝트 생성 시 문항 고정, 최종 제출 시 문항·답변·사원정보 고정. 최종 제출 수정·재개 및 기록이 있는 배정·프로젝트 삭제 차단 |
| 명부 소속 상속 | 실제 부서가 바뀌면 이전 팀 상속 초기화. 업로드 전 변경 미리보기 및 원자적 반영 |
| 전화번호 소실 | 조회에 전화번호 포함. 수정 요청에서 생략되거나 업로드 셀이 비어 있으면 기존 번호 유지 |
| PDF 유형 혼입·HTML 삽입 | 해당 기록의 고정 문항으로 생성. 문항·사원정보·답변을 HTML 이스케이프하고 PNG 서명만 허용 |
| Excel 누락·총점 변경 | 배정별 한 행 생성. 대기·임시저장·부서 공란도 포함. 고정 기록의 답변 합계 사용. 문자열은 수식으로 실행되지 않게 저장 |
| 구형 DB 자료 소실 | 웹 시작 시 기존 DB 자동 변경 금지. 백업 후 명시적 이전. 원래 열의 모든 값·ID·건수·해시, 외래키 및 무결성 대조. 실패 시 전체 롤백 |
| 제출 검증 부족 | 배정과 사원 ID 일치, 기간, 문항 버전·소속, 중복·누락, 점수 범위, 답변 길이, 유효한 비어 있지 않은 PNG 서명 검증. 동시 제출 직렬화 |

기존 프로젝트는 **기존 평가** 회차로 묶는다. 과거 연도·차수는 임의로 추정하지 않는다. 이전 자료의 완료 기록은 이전 시점에 DB에 남아 있는 문항·인적사항·답변을 보존한다. 이미 변경된 옛 이름·문항 또는 당시 점수 척도는 이 DB만으로 복원할 수 없다. 옛 점수를 변환하지 않으며, 객관식 만점은 `기존 척도 미확인`으로 표시한다. 기존 답변에 다른 유형 문항이나 중복 답변이 있으면 삭제 없이 보존하고 비고에 표시한다. 새 입력 문항에는 다른 유형을 포함하지 않는다.

새 문항 척도는 기존 화면과 동일한 6~10점이다. 문항 편집은 이후 생성한 프로젝트에 적용된다. 기존 프로젝트의 문항은 고정되므로 문항을 바꿔 다시 평가하려면 새 회차·프로젝트를 만든다. 임시 저장은 수정 가능하며, 최종 제출 후에는 고정된다. 평가 기록이 있으면 전체 명부 초기화도 차단된다.

## 배포 전 준비

1. 실제 호스팅 업체, 프로젝트 경로, Python 가상환경, WSGI 설정, **실제 사용 중인 DB 절대경로**를 확인한다. `SMART_EVALUATOR_DB`로 경로를 명시한다. 기본 경로에 의존해서 다른 DB를 생성하지 않는다.
2. 현재 운영 코드·정적 파일·설정을 별도 보관한다. DB 백업은 웹 정적 경로나 공개 다운로드 경로에 두지 않는다.
3. 운영 DB의 읽기 전용 복제본으로 아래 `dry-run`을 먼저 실행한다. 최종 운영 백업과 이전은 모든 쓰기가 중단된 후 다시 수행한다. 사용자가 제공한 다운로드 백업이 최신 운영 DB와 같다고 가정하지 않는다.
4. 운영과 같은 Python 환경에 `backend/requirements.txt` 의존성을 준비한다. 이 패키지는 빌드된 `backend/static`을 포함하므로 서버에서 프런트엔드를 다시 빌드할 필요는 없다.

명령 예시는 Linux 운영 서버용이다. `APP_DIR`, `DB_FILE`, `BACKUP_DIR`를 실제 값으로 교체한다. `python`은 운영 가상환경의 Python이어야 한다.

```sh
APP_DIR=/absolute/path/to/SmartEvaluator
DB_FILE=/absolute/path/to/employees.db
BACKUP_DIR=/private/path/to/evaluator-backups
cd "$APP_DIR"
python -m pip install -r backend/requirements.txt
python backend/manage_db.py inspect --db "$DB_FILE"
python backend/manage_db.py dry-run --db "$DB_FILE"
```

`inspect`는 건수·해시·무결성을 출력한다. `dry-run`은 임시 복제본을 이전하고 원본 DB에는 쓰지 않는다. `preserved` 결과의 각 테이블 건수·해시가 이전 검증의 근거다. 불일치나 외래키 오류가 있으면 운영 이전을 하지 않고 원본 관계를 조사한다.

## 운영 적용 순서

1. 점검 시간을 안내하고 호스팅 설정에서 모든 기존 웹 워커, 별도 작업, DB 쓰기 요청을 중단한다. **구버전 코드는 점검 파일을 확인하지 않으므로 `pause` 명령만으로 기존 서버가 중단되지 않는다.** 중지 방법은 실제 호스팅 환경에 맞춰 확인한다.
2. 쓰기가 중단된 운영 DB와 현재 코드를 함께 백업한다. SQLite의 파일 복사보다 아래 SQLite 백업 명령을 사용한다.
3. 새 `backend` 코드와 정적 파일을 배치하고 기존 운영 DB의 명시적 경로로 이전한다. 패키지에 DB는 없으며, 운영 DB를 빈 파일로 교체하지 않는다.

```sh
python backend/manage_db.py pause --db "$DB_FILE"
python backend/manage_db.py backup --db "$DB_FILE" --backup-dir "$BACKUP_DIR"
python backend/manage_db.py migrate --db "$DB_FILE" --backup-dir "$BACKUP_DIR" --maintenance
python backend/manage_db.py inspect --db "$DB_FILE"
```

`migrate`도 자체 백업을 만들며, 성공·실패 모두 점검 표시를 유지한다. 같은 버전에 재실행하면 자료를 다시 가공하지 않는다. 이전은 트랜잭션으로 수행하며 원본 열의 값과 건수를 대조한 뒤에만 커밋한다. 백업 이후 쓰기가 발견되면 중단한다.

4. WSGI에서 `main`을 import하기 **전에** `os.environ['SMART_EVALUATOR_DB']`에 실제 DB 절대경로를 설정하고 새 코드를 재시작한다. 현재 `backend/wsgi.py`의 경로 설정은 환경에 맞춰 유지한다. 점검 중에는 조회만 허용되며 모든 쓰기는 503으로 차단된다. 이 단계에서 로그인도 차단되므로 기존 관리자 화면 또는 읽기 전용 API로 조회를 확인하고, 로그인은 재개 직후 확인한다.
5. 이전 결과의 보존 건수·해시와 무결성을 확인한다. 완료 평가 몇 건의 문항, 점수, 서술형, 서명, 이름을 이전 전 자료와 대조하고 PDF·Excel을 내려받아 확인한다. Excel은 전체 배정 수와 행 수가 같아야 한다. 기존 점수를 새 척도로 재계산하지 않아야 한다.
6. 검증이 끝나면 재개한다. 사용자는 반드시 새로고침해 새 화면을 받아야 한다. 구버전 화면의 쓰기 요청은 409로 차단된다.

```sh
python backend/manage_db.py resume --db "$DB_FILE"
```

재개 직후 관리자·사원 로그인, 신규 회차 생성, 테스트용 신규 배정의 임시 저장·최종 제출, 최종 제출 수정 차단, PDF·Excel을 확인한다. 실제 사원의 기존 완료 평가를 테스트용으로 재제출하지 않는다. 신규 입력 검증은 별도 시험 DB에서 먼저 끝낸다.

## 실패·복구

이전 실패 시 자동 롤백되며 점검 표시는 남는다. 오류를 해결하기 전 `resume`하지 않는다. 백업 경로와 오류 로그를 보관한다.

서비스 재개 **전** 새 버전을 철회해야 한다면 모든 워커를 중지한 상태에서 백업의 무결성을 확인하고, 이전 전 **코드·정적 파일·DB를 함께** 복구한다. SQLite WAL/SHM 파일이 남아 있다면 이전 작업자가 열린 연결이 없음을 확인하고 일관된 백업을 복원해야 한다. 구버전 코드를 새 DB에 연결해 자동 초기화시키지 않는다.

서비스 재개 **후**에는 새 제출이 존재할 수 있으므로 옛 DB를 바로 덮어쓰지 않는다. 쓰기를 다시 중단하고 현재 DB를 먼저 백업한 뒤 신규 기록을 포함하는 복구 방안을 정한다. 이전 전 백업만 복원하면 재개 후 제출을 잃게 된다.

## 로컬 검증 명령

프로젝트 루트에서 운영 DB를 지정하지 않고 실행한다. 기본 테스트는 자체 임시 DB만 사용한다.

```sh
python -m unittest discover -s backend/tests -v
cd frontend
npm ci
npx eslint src/components/AdminDashboard.jsx src/components/EvaluationForm.jsx src/api.js
npm run build
```

실제 백업 보존 검사도 실행하려면 `EVALUATOR_TEST_BACKUP`에 별도 백업 절대경로를 지정한다. 테스트는 읽기 전용 연결로 임시 복제본을 만들고, 종료 시 원본 SHA-256이 그대로인지 확인한다. 기존 App/Login/Dashboard의 전체 린트 오류는 이번 수정에서 제외한 영역에 남아 있다.
